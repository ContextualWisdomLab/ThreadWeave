# ThreadWeave 0.2.0 Release Design

## Decision

Release ThreadWeave 0.2.0 through one manually dispatched, main-only workflow. The
workflow builds and verifies the package from the reviewed source commit, moves a
single immutable artifact bundle through isolated jobs, generates GitHub build and
SBOM attestations, creates an annotated tag and GitHub Release, and finally uploads
the exact wheel and source distribution to PyPI with OIDC Trusted Publishing.

This is preferred over a tag-triggered workflow because the repository does not
currently have an authenticated mechanism available to this maintenance loop for
creating a tag. The manual version input is treated only as untrusted text: a
release-contract program validates it against the reviewed source before any tag,
release, or publication privilege is used.

## Release boundary

The requested version, `[project].version`, `threadweave.__version__`, annotated
tag, distribution filenames, package metadata, and one dated CHANGELOG section must
all resolve to the same canonical three-part final version. For this release that
value is `0.2.0`, the tag is `v0.2.0`, and the release date is `2026-08-04`.

The accumulated `Unreleased` entries become the 0.2.0 release notes. A new empty
`Unreleased` section remains at the top so later development does not append to a
published historical section.

## Components

### `scripts/ci/release_contract.py`

A standard-library-only program owns all metadata and evidence rules. It:

- parses `pyproject.toml` with `tomllib`;
- parses the literal `__version__` assignment without importing package code;
- rejects noncanonical, prerelease, duplicate, mismatched, or placeholder metadata;
- extracts exactly one material CHANGELOG section;
- requires exactly one wheel and one source distribution for the reviewed version;
- writes release notes, sorted SHA-256 checksums, and a deterministic SPDX 2.3 JSON
  document;
- emits bounded GitHub Actions outputs; and
- converts contract failures into an explicit nonzero exit status without a stack
  trace that could obscure the actual release error.

The SPDX document describes the released ThreadWeave package and every published
distribution file. ThreadWeave has zero runtime dependencies, so no dependency
packages are fabricated into the SBOM.

### `.github/workflows/release.yml`

The workflow is `workflow_dispatch` only and accepts one required `version` input.
It rejects invocations outside the canonical repository or protected `main` branch.
Concurrency is keyed by the validated user-supplied version and never cancels an
in-progress release.

Privileges are split across fresh jobs:

1. **build-release** has read-only repository access. It installs the existing
   hash-locked CI toolchain, repeats lint, compilation, doctests, complete tests and
   100% coverage, builds with isolation disabled, verifies the wheel outside the
   source tree, runs the release contract, and uploads one named bundle.
2. **attest-release** receives only the bundle plus OIDC/attestation permissions.
   It creates SLSA provenance and an SPDX SBOM attestation for the distribution
   artifacts.
3. **tag-release** receives only contents-write permission. It verifies that any
   existing remote tag resolves to the exact reviewed commit; otherwise it creates
   and pushes one annotated tag.
4. **github-release** receives contents-write permission and creates or repairs the
   GitHub Release with `--verify-tag`, release notes, wheel, sdist, checksums, and
   SBOM.
5. **publish-pypi** runs only after build, attestation, tag, and GitHub Release
   success. It uses the dedicated `pypi` environment, `id-token: write`, and the
   official PyPA publisher action. It has no password, API token, or
   `skip-existing` escape hatch.

Every third-party action is pinned to a full commit SHA. The build job never shares
an execution context with tag, GitHub Release, attestation, or PyPI publication
credentials.

## Retry and failure behavior

A failed build, test, metadata check, artifact check, attestation, or tag check
prevents publication. Retrying the same version is safe only when the existing tag
still identifies the reviewed main commit. GitHub Release creation is idempotent:
an existing release is updated with the same reviewed artifacts. PyPI remains
immutable and fail-closed; the workflow never ignores an already-published version.

The external prerequisite is a pending or existing PyPI Trusted Publisher for:

- owner: `ContextualWisdomLab`;
- repository: `ThreadWeave`;
- workflow: `release.yml`;
- environment: `pypi`; and
- project name: `threadweave`.

The workflow must expose a clear OIDC failure when that publisher is absent rather
than falling back to a long-lived secret.

## Quality evidence

The release PR must retain:

- Python 3.10–3.13 CI;
- 100% production statement and branch coverage;
- 100% autonomous-boundary statement and branch coverage;
- complete production and release-tooling docstrings;
- byte-for-byte dependency-lock regeneration;
- hash-checked dependency and wheel installation;
- SAST Semgrep and repository Security Scan success;
- CodeRabbit/current-head review with no unresolved threads; and
- wheel/sdist content and outside-source-tree import smoke tests.

## Standards and authoritative guidance

The release contract uses canonical final versions compatible with PEP 440,
SPDX 2.3 JSON for the software bill of materials, GitHub artifact attestations for
build provenance, and PyPI Trusted Publishing for short-lived OIDC credentials and
PEP 740 publish attestations.
